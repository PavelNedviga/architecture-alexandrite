# Выбор и настройка мониторинга в системе

## Анализ системы компании и C4-диаграммы в контексте планирования мониторинга

## Мотивация

Напишите здесь, почему в систему нужно добавить мониторинг и что это даст компании.

| Бизнес‑боль                                                                                                                                                     | Как решает мониторинг                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Клиенты и B2B‑партнёры жалуются на просрочку заказов, команда узнаёт об инцидентах из тикетов | **Проактивные алерты**по задержкам расчёта, росту очередей или ошибкам API позволят реагировать до жалобы |
| Операторы видят «висящие» заказы, страница MES грузится медленно                                                      | **Метрики производительности**front‑ и back‑эндов + нагрузка БД позволят найти узкие места                                   |
| Нет понимания, где узкое место при росте заказов                                                                                   | **Наглядные дашборды**с RPS, latency, CPU/RAM, глубиной очередей дадут картину системы «end‑to‑end»                                   |
| Релизы сдвигаются, потому что ошибки всплывают поздно                                                                        | **SLO/SLA‑метрики**и автоматические проверки в CI/CD (smoke‑тесты на метрики) снижают риски отката                            |

**Мониторинг** — это «датчики» бизнеса; без них компания «летит вслепую», что уже привело к потере контрактов. Без мониторинга мы можем вкладывать ресурсы на устранения проблем, которые локализованы вовсе не там, где кажутся на основе субъективных предположений и полагаясь на опыт команды.

## Выбор подхода к мониторингу

Выберите, какой подход к мониторингу вы будете использовать: RED, USE или «Четыре золотых сигнала». Для разных частей системы можно использовать разные подходы.

| Сегмент                                          | Подход                                                                               | Почему                                                                                           |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **API‑сервисы**(Shop, CRM, MES)           | **RED**(Rate‑Errors‑Duration)                                                      | Главная ценность — скорость и успешность запросов           |
| **RabbitMQ, очереди S3‑расчётов** | **USE**(Utilization‑Saturation‑Errors)                                             | Ключевой риск — переполнение и «застревание» сообщений |
| **Инфраструктура (EC2/БД/S3)**    | **Четыре золотых сигнала**(Latency, Traffic, Errors, Saturation) | Нужно понимать и ресурсное потребление, и доступность    |

  * Smoke‑тест после деплоя: метрика `api_up == 1`, p95 latency < threshold.
